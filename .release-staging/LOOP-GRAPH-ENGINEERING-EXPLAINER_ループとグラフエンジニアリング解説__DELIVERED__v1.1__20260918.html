1. 用語の定義

用語Loop Engineering と Graph Engineering は、単一の標準規格で定義された固定用語ではない。 本資料では、AIエージェントの反復処理、状態機械、ワークフローグラフ、再試行・復旧設計を構造的に説明するための整理軸として使用する。
定義

Graph Engineering

作業をNode（処理単位）、Edge（遷移）、State（状態）、Guard（遷移条件）、Gate（通過条件）、Terminal（終了状態）へ分解し、実行経路を明示的に設計すること。

定義

Loop Engineering

失敗・不足・検査NG・外部中断などから再度処理を行う際に、戻り先、再実行条件、差分、上限、エスカレーション、重複副作用防止を設計すること。

事実一般的なAgent Runner（エージェント実行器）では、LLM呼出し→出力判定→Tool実行またはHandoff→再度LLM呼出し、という反復が実装される。OpenAI Agents SDKもこの構造を明示している。

2. なぜ制御構造が必要か

LLMは「次に何をするか」を柔軟に判断できる一方、長い業務処理全体の状態・依存・再試行・完了条件までLLM自身に委ねると、再現性と監査可能性が落ちる。

確率的な判断

同じ目的でも、LLMが選ぶ説明順、Tool、探索範囲、終了タイミングは揺らぎ得る。

副作用

ファイル書込、API更新、デプロイなどは「もう一度実行してよいか」を自然言語だけでは安全に決めにくい。

完了の曖昧さ

「回答が出た」「Tool呼出しが止まった」と「業務上の完了」は同じではない。

設計上の整理LLMには曖昧な判断を担当させ、状態遷移・回数制御・権限・完了判定のような機械的規則は外側の制御層へ置くのが、複雑な実行系を理解しやすくする基本構造である。妥当性 97%。

3. Graph Engineering — 全体の仕事を「経路」にする

要素役割実装時に決めること
State（状態）現在どこまで進んだかを表す状態Schema、更新権限、永続化、再開方法
Node（処理単位）1つの仕事を実行する入力、出力、責務、Tool権限、終了条件
Edge（遷移）次に進むNodeを決める固定遷移か条件分岐か、並列化の有無
Guard / Gate進んでよい条件を判定するSchema、検証結果、承認、Evidenceの必要条件
Terminal（終了）Graph全体の終端を定義する完了、失敗、保留、要判断をどう区別するか
事実LangGraphは、GraphをState・Nodes・Edgesで構成し、条件Edgeによる分岐やLoopを表現する。AWS Step FunctionsもState MachineとしてTask、Choice、Retry、Catchなどを明示的に定義する。

4. Loop Engineering — 「やり直す」を設計可能にする

Loopは単に「失敗したらもう一回」ではない。重要なのは、前回と何が変わったから再実行する価値があるのかを定義することである。

設計項目問い悪い例良い例
Trigger何が起きたら戻るか「失敗したら」「必須Evidenceが欠落」「Test ID T-103がNG」
Return Targetどこへ戻すか最初から全部不足の責務を持つNodeだけ
Required Delta何が変われば再実行するか同じ入力で再試行新Evidence、修正差分、別観測結果
Retry Budget何回までか無限同一Failure SignatureはN回まで
Escalation収束しないときどうするか黙って再試行再計画、人判断、HOLDへ遷移
Idempotency再実行しても副作用は重複しないか毎回書込実行ReceiptやIdempotency Keyで保護

5. 一般的なHarness（実行制御基盤）の構造

Harnessは、LLMの能力そのものではなく、LLMを安全に・再現可能に・継続実行させるための外側の実行基盤として考えると理解しやすい。

LAYER 1入口 / Contract利用者要求を目的、Scope、制約、受入条件、許可操作へ正規化する。
LAYER 2Control PlaneGraph、State、権限、再試行、復旧、完了判定を管理する。
LAYER 3Agent / Tool RuntimeLLM、Tool、Agent、SkillをNodeごとに実行する。
LAYER 4Knowledge / Evidenceコード、文書、DB、ログなどの根拠と関係を検索・固定する。
LAYER 5Verification出力Schema、Test、独立検査、残件、完了条件を判定する。
利用者要求
   │
   ▼
[Contract / Intent]
   │
   ▼
[Control Plane]
   ├── Work Graph ── Node / Edge / State / Gate
   ├── Loop Policy ─ Retry / Rework / Recovery / Escalation
   ├── Permission  ─ Tool / Write / External Side Effect
   └── Completion  ─ Terminal / Open Obligations
          │
          ▼
[Agent / Tool Runtime] ── LLM / Tool / API / Code
          │
          ├──────────────► [Knowledge / Evidence Store]
          │
          ▼
[Verifier / Test / Schema Check]
          │
          └── PASS → 次Node / END
              FAIL → Loop Policyに従って戻す
設計上の整理「Agentを賢くする」だけではなく、Agentの外側にGraphとLoopを置くことで、確率的な判断と決定論的な制御を分離できる。妥当性 98%。

6. Outer Graph（外側の作業グラフ）と Inner Agent Loop（内側の反復）

Outer Graph

業務全体の順序、依存、並列化、品質Gate、権限、残件、完了条件を管理する。複数Agentや非LLM処理をまたぐ。

Inner Agent Loop

1つのNode内部で、LLMがToolを呼ぶ、結果を読む、追加Toolを呼ぶ、最終出力を返すという反復を行う。

事実OpenAI Agents SDKのRunnerは、最終出力、Handoff、Tool callを判定しながら反復する。これは典型的なInner Agent Loopである。一方、複数工程の業務完了条件は別のワークフロー制御として設計できる。
混同すると起きる問題：Agentが「終了」と返しただけで業務全体を完了にする、あるいは1つのAgent Loopに分析・実装・検証・承認まで詰め込み、責務と失敗箇所が追えなくなる。

7. Work GraphとKnowledge Graphは別物

Work Graph（作業グラフ）Knowledge Graph（知識グラフ）
目的「次に何をするか」を決める「何と何が関係しているか」を表す
Nodeの例影響分析、実装、レビュー、Testプログラム、Table、API、設計書、Test Case
Edgeの例PASSならReviewへ、NGなら修正へAがBを呼ぶ、CがDを更新する
状態READY / RUNNING / FAILED / DONEなどRelation、Evidence、Confidence、Freshnessなど
更新契機実行イベント解析・索引更新・資産変更
関係：Knowledge Graphから取得した依存関係やEvidenceを、Work GraphのNodeが入力として使う。つまり「知っている構造」と「進める構造」を分離し、必要なところで接続する。

8. Node・Agent・Skill・Controllerを分ける

Graphを作るときに最も混乱しやすいのが、「何をNodeにするか」「Agentは何個必要か」である。以下の分離で整理しやすくなる。

Node

あるRunにおける作業の実体。「このモジュールの影響分析」など、対象付きの実行単位。

Agent

判断責務。「影響分析を行う」「レビューする」など、再利用可能な役割契約。

Skill / Tool

実行手段。Git操作、SQL解析、Java解析、Web取得など。

Controller

機械的な制御。次Node選択、Retry回数、権限、Scope、完了判定など。

設計上の整理同じAgentを複数Nodeで再利用し、同じSkillを複数Agentが使う多対多構造にすると、責務と実行対象を分離しやすい。妥当性 96%。

9. 構造化Handoff（引継ぎ）

Agent同士を自由文だけで接続すると、「何が確定し、何が未確定で、次の担当が何を信頼してよいか」が曖昧になる。引継ぎはSchema（構造）を持たせる。

{
  "taskId": "TASK-1042",
  "sourceNode": "impact-analysis",
  "targetNode": "implementation",
  "artifactIds": ["ART-21", "ART-22"],
  "evidenceIds": ["EV-883", "EV-884"],
  "decisions": [
    {"id": "DEC-31", "status": "CONFIRMED"}
  ],
  "openObligations": [
    {"id": "OB-7", "reason": "API仕様未取得"}
  ],
  "completionResult": {
    "status": "PASS_WITH_OPEN_ITEM",
    "failureSignature": null
  }
}
ポイント：自然言語は説明用に残してよいが、次工程の制御に使う値はID・状態・Schemaで受け渡す。

10. 開発作業の具体例

例：不具合修正

01受付症状、Scope、再現条件を契約化
02再現失敗Evidenceを固定
03原因分析候補と反証を整理
04修正許可Scope内だけ変更
05Test再現Testと回帰Test
06Review独立検査
07完了残件0とEvidenceを確認

ここでTestがNGなら、Graph全体を最初から実行し直す必要はない。Failure Signature（失敗特徴）から原因分類Nodeまたは修正Nodeへ戻し、修正差分と回帰範囲が変わったことを確認して再実行する。これがLoop Engineeringである。

例：影響調査

Knowledge Graphで呼出関係・CRUD・Data Lineage（データの流れ）を探索し、その結果をEvidenceとしてWork Graphの「影響閉包」Nodeへ入力する。未確認候補が残ればLoopし、全候補が「対象／対象外／未解決」に分類されたら次工程へ進む。

11. 典型的な失敗設計

巨大Agent：分析・実装・レビュー・完了判定を1つのAgentに持たせる。自己承認と責務混在が起きる。
無限Retry：同じ入力・同じTool・同じFailure Signatureで繰り返す。計算量だけ増えて情報は増えない。
自由文Handoff：次工程が前工程の「要約」を信頼するしかなく、未確定事項やEvidenceが落ちる。
GraphとKnowledgeの混同：資産依存関係と作業順序を同じGraphで表し、意味の異なるEdgeが混在する。
LLMに状態遷移を全面委任：「もう十分」とModelが判断した時点を業務完了としてしまう。
副作用の再実行保護なし：Crash後の再開で、書込・通知・デプロイが二重実行される。

12. 設計レビュー観点

GraphのSTART、Terminal、失敗終端、保留終端が明示されている。
各Nodeの入力・出力・責務・権限・完了条件が定義されている。
条件分岐が自然言語の雰囲気ではなくState値で説明できる。
LoopごとにTrigger、戻り先、Required Delta、上限がある。
同じFailure Signatureを無制限に再試行しない。
Crash再開時に完了Nodeと副作用を重複実行しない。
Agentの自己申告だけでGraph全体を完了にしない。
Work GraphとKnowledge Graphの責務が分かれている。
HandoffにArtifact、Evidence、Decision、Open ItemのIDがある。
生成担当と検証担当の独立性が必要な箇所を分けている。
まとめGraph Engineeringは「仕事の地図」を設計し、Loop Engineeringは「地図の途中で問題が起きたときの戻り方」を設計する。 Harnessは、その地図と戻り方をLLMの外側で実行・監視する基盤である。妥当性 99%。
