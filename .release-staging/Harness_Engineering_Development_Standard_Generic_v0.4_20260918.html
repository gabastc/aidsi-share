0. 概要

結論：ハーネスエンジニアリングが開発すべきものは、業務や製品に固有な「制御・構成・責務分離・接続・根拠・検証」である。一方、Tokenizer（トークナイザー：文章をトークンへ分割する基盤機能）、推論エンジン、Attention / KV Cache（推論高速化の内部機構）、汎用Sampling（候補選択）、一般的なモデルServing（配信）などは、通常は生成AI基盤側をそのまま使う方がよい。

事実 生成AIを業務へ適用するとき、実際に設計対象になるのは「モデルそのもの」よりも、入力をどう整え、どの責務へ渡し、どの順序で処理し、どの外部系へ安全につなぎ、出力をどう検証して配布するかという周辺構造である。
見解 ハーネスエンジニアリングの中心は、AIを賢くすることではなく、AIを業務で安全・再現可能・監査可能に働かせる構造を作ることにある。妥当性は 98%。

ハーネスの目的

AIの能力をそのまま信じるのではなく、入力・判断・外部連携・証拠・完了判定を構造化する。

構造理解の要点

「利用体験」「制御」「判断」「接続」「根拠」「検証」「基盤」の7視点に分けると理解しやすい。

配置判断の要点

症状が出た場所ではなく、守るべき不変条件を恒久的に所有すべき要素へ配置する。

1. ハーネスエンジニアリングとは何か

ハーネスエンジニアリングとは、生成AIを単体で使うのではなく、業務目的に沿って安全・安定・再利用可能に動作させるための周辺構造を設計・実装・運用することである。

1.1 「モデル開発」との違い

観点モデル開発ハーネスエンジニアリング
主対象学習済みモデル、重み、推論品質業務適用の構造、制御、接続、検証
主な成果精度、速度、学習結果安全に使える業務システム、作業フロー、証拠、配布物
典型的な関心トークナイザー、推論最適化、GPU効率、デコーダ入力設計、役割分担、権限制御、監査、再実行安全性
変更頻度基盤更新時業務要件・接続先・運用要求の変化時

1.2 ハーネスの役割

  • 利用者の依頼を、AIが処理できる形へ変換する
  • 必要な文脈・資料・ソースコード・履歴を収集する
  • どのAI役割が何を担当するかを分離する
  • 外部システム更新や配布を安全に制御する
  • 結果が要件を満たしたかを検証する
  • 同じ品質を繰り返し再現できるようにする

2. ハーネス全体構造の図解

ハーネスは、生成AIモデルそのものではなく、モデルの外側で「入力・規約・制御・判断・接続・根拠・検証」を組み合わせる実行構造です。製品ごとの名称ではなく、まず以下の一般構造を理解します。

図1：ハーネスエンジニアリングの一般構造
① Interface / Ingress（利用者入口）Chat、CLI、IDE拡張、設定画面、コマンド、進捗・エラー表示。利用者から仕事を受け取る層。
↓
② Policy / Instruction（規約・指示）プロジェクト規約、禁止事項、命名規則、成果物条件、作業上の前提。「AIへ何を守らせるか」を定義する層。
↓
③ Orchestration / Control（工程制御）Workflow、Graph、状態遷移、分岐、再試行、排他、権限、Hook、Guard、完了判定。「いつ・何を・どの順番で実行するか」を強制する層。
↓
④ Reasoning Role / Procedure（判断責務・作業手順）Agent、Subagent、Role、Skill、Procedure。設計・分析・レビューなど「AIに何を考えさせるか」と、その標準手順を定義する層。
↓
⑤ Tool / Context / Knowledge Access（道具・文脈・知識アクセス）Tool、Adapter、MCP、検索、Git、DB、文書、課題管理、静的解析、Evidence、Knowledge。「AIが何を読めるか・操作できるか」を定義する層。
↓
⑥ Verification / Observability / Distribution（検証・観測・配布）検証、Readback、Traceability、ログ、監査証跡、Package、署名、Release、導入確認。「本当に正しくできたか」を証明する層。
↓
⑦ GenAI Runtime / Foundation（生成AI基盤）Tokenizer、Embedding、Transformer、Attention、KV Cache、Sampling、Batching、Model Serving。通常は既存基盤をそのまま利用する。
構造上のポイント①〜⑥が主にハーネスエンジニアリングの開発対象、⑦が主に生成AI基盤側です。上へ行くほど業務固有、下へ行くほど共通基盤になります。
見解製品名や設定ファイル名より先に、この7層構造で「どこが責任を持つべきか」を理解すると、Codex・Claude Code・Cursorなど製品が変わっても設計判断を再利用できます。妥当性は 99%。

3. 開発する要素 / 開発しない要素

図2：ハーネスエンジニアリングとして開発する要素

  • 利用者入口、初回設定、診断、設定画面
  • 依頼の分類、権限区分、作業契約
  • 工程制御、状態遷移、再開、排他、完了判定
  • 役割別Agent、プロンプト方針、出力契約
  • 業務システム接続、Adapter、静的解析、知識化
  • 証拠管理、追跡可能性、Readback
  • 検証、配布、導入確認、Release
業務固有監査対象要件差が出るハーネスの価値そのもの

図3：通常は生成AI基盤をそのまま使う要素

  • Tokenizer（トークナイザー）
  • Embedding Encoder（埋め込み生成器）
  • Transformer / Attention 本体
  • KV Cache、Paged Attention 等の推論高速化機構
  • Decoding / Sampling（生成候補の選択）
  • Batching / Scheduling（推論実行の束ね処理）
  • Model Serving Runtime（モデル配信基盤）
  • ベンダーSDKの低レベル通信
共通基盤業務差が少ない再実装コスト大保守責任が重い
重要：「開発しない」は「絶対に触れない」ではない。例えばオンプレミス推論、厳しいコスト制約、独自モデル、特殊なマルチモーダル最適化がある場合は基盤側を調整することもある。ただし、その場合はハーネス拡張ではなく、モデル基盤開発として別の責務で扱う。

以下は製品固有ではなく、ハーネスエンジニアリングとして一般化した構成要素です。

5.2 Instruction・Skill・Hookで迷う場合

Policy / Instruction

「普段から守ること」
短い規約・禁止事項・プロジェクト方針。

Procedure / Skill

「この仕事のときに使う詳しい手順」
レビュー、Release、障害調査など。

Controller / Hook

「AIが忘れても必ず強制すること」
危険操作拒否、編集後検査、監査ログ等。

見解「AIへ伝える情報」「AIに考えさせる仕事」「AIの外側で強制する制御」を分けると、配置判断が最も安定します。妥当性は 99%。

6. 要素別の配置基準

6.1 Interface / Ingress に配置する場合

  • 利用者が迷う、入力しにくい、状況が分からない
  • 前提不足を事前に診断したい
  • エラーを利用者向けに翻訳したい

置かない方がよいもの：承認可否の正本、工程完了判定の正本、外部更新の最終実行判定。

6.2 Policy / Instruction に配置する場合

  • 調査なのか、修正なのか、レビューなのかで処理を変える
  • READ_ONLY（読取専用）か CHANGE_ALLOWED（変更許可）かを分ける
  • 成果物形式や必須出力を固定する

6.3 Orchestration / Graph に配置する場合

  • 工程の数や順番を変えたい
  • レビュー後だけ配布へ進みたい
  • 失敗時にどこへ戻すかを固定したい

6.4 Controller / Guard / Hook に配置する場合

  • 同じ入力なら必ず同じ判定にしたい
  • 権限、排他、Scope、完了条件を機械的に守りたい
  • DB更新やRelease作成など外部副作用を安全に実行したい

6.5 Reasoning Role / Agent に配置する場合

  • 文書要約、設計案作成、説明文生成、レビューコメント作成のように、意味理解や推論が必要
  • 同じ根拠でも複数の妥当な表現があり得る
  • 出力が文章や提案であり、後続で検証可能

6.6 Tool / Adapter / MCP に配置する場合

  • 機能の本質は同じで、接続先だけが違う
  • 課題管理製品やストレージ製品の差を吸収したい
  • 認証方式差、API差、データ形式差が主要論点

6.7 Context / Knowledge / Evidence に配置する場合

  • AIが必要な根拠を持てていない
  • ソースコードや文書から構造情報を抽出したい
  • 変更影響範囲を事実ベースで絞りたい

6.8 Verification / Distribution に配置する場合

  • 成果物が本当に成立しているかを証明したい
  • Package後、Installer後、配布後の起動確認が必要
  • 公開、更新、Rollback を扱いたい

6.9 GenAI Runtime / Foundation をそのまま使う場合

  • 要件差が小さく、共通基盤のままで十分
  • カスタマイズコストより利用価値が低い
  • 業務差分がTokenizerやSamplingではなく、その前後の制御や文脈にある

8. アンチパターン

1
何でもAgentに入れる。
制御や機械判定までLLMへ委ねると、再現性・監査性・安全性が下がる。
2
UIで症状だけを隠す。
根本原因が配布物や制御にあるのに、入口だけ修正すると別経路で再発する。
3
接続先ごとにWorkflow全体を複製する。
Provider差はAdapterで吸収し、全体制御を複製しない。
4
Tokenizerや推論基盤を安易に作り直す。
再実装コストと保守責任が大きく、業務価値に直結しにくい。
5
完了判定を複数箇所に持つ。
UI、Agent、Controller、テストで別々の完了条件を持つと整合しなくなる。
6
局所テストだけで完了とする。
入口から終端までの代表経路を通さず、通常運用で使えない状態を見逃す。

9. 実装・検証・レビュー観点

9.1 実装観点

  • Primary Owner（主責任要素）は1つに固定されているか
  • 同じ判定や状態の正本が複数に増えていないか
  • 判断と制御が分離されているか
  • 接続差だけで全体構造を複製していないか

9.2 検証観点

  • 要素の直接試験：その要素の責務を単体で検証できるか
  • 代表経路試験：入口から終端まで正常に流れるか
  • 再実行安全性：同じ実行を繰り返しても破壊的副作用が増えないか
  • Readback：保存・公開・配布後の実体を再取得して確認しているか

9.3 レビュー観点

  • なぜその機能をその要素へ置いたのか説明できるか
  • 基盤側でよいものをハーネス側へ持ち込んでいないか
  • ハーネス固有の価値を出す部分へ工数が使われているか
  • 運用負荷を増やすだけの構成追加になっていないか

実務運用のコツ： 新しい要素を作る前に、まず REUSE（再利用） → EXTEND（既存拡張） → ADAPT（接続差吸収） → COMPOSE（組合せ） を確認し、それでも無理なときだけ CREATE（新設） とする。

11. 開発上の主要留意点 — AIメーカー公式ガイダンスから抽出した共通原則

ハーネスエンジニアリングでは、Context量だけでなく、権限、実行境界、外部情報の信頼性、Tool設計、検証、承認、Agent分割、監査、回復性まで設計対象にする必要があります。本章はOpenAI、Anthropic、Cursorの公式文書に現れる主要な注意事項を、製品固有機能ではなく一般的な開発標準へ変換したものです。

共通傾向 3社の表現や実装方法は異なりますが、共通して「LLMへの指示だけに依存しない」「Tool権限を限定する」「外部入力を信用しない」「重要操作には追加制御を置く」「結果を検証する」「実行を観測可能にする」という多層防御の考え方が確認できます。

11.1 Contextは有限資源として扱う

原則： 常時Contextへ入れる情報は最小化し、必要なRule、Skill、資料、Toolだけを必要時にロードする。

  • 長いInstruction、会話履歴、Tool定義、MCPカタログ、資料を全部投入しない。
  • 詳細な作業手順はProcedure / Skillへ分離する。
  • 調査はSubagent等の別Contextへ分離し、主Contextには結論と根拠だけを返す。
  • Compaction（文脈圧縮）を前提に、重要なID・決定・未完事項・成果物位置を外部Stateへ保存する。
設計上の注意： 「重要だからInstructionを増やす」は逆効果になり得ます。Anthropicは長いContextで以前のInstructionを忘れたり誤りが増え得ることを明記し、CursorもSummaryへの圧縮に情報損失があることを説明しています。OpenAIもSkillsやInstruction filesの競合を監査するよう推奨しています。

11.2 最小権限と「読取 / 変更」の分離

原則： Agentへ最初から広い権限を渡さない。読取、編集、Shell、Network、外部更新を別権限として扱う。

操作標準理由
ファイル・資料の読取必要Scopeのみ許可不要な機密情報やPrompt Injection源をContextへ持ち込まない
ファイル編集Workspace / Repository境界内へ限定意図しない領域の変更を防ぐ
Shell実行Sandbox + allow / ask / denyLLMの誤判断をOS境界で抑える
外部更新対象・操作種別を限定メール送信、課題更新、DB更新等の副作用を局所化する
Network必要先のみAllowlist情報流出・Prompt Injection後の外部送信を制限する

AnthropicはPermission ruleを「モデルではなくClaude Code側で強制」と明記し、CursorもSandbox・Permission・Network controlの併用を案内しています。OpenAIもAgentのSensitive data / credential accessを必要最小限へ限定することを推奨しています。

11.3 Prompt / Ruleは「誘導」、必須制約は決定論的に強制する

原則： 「絶対にしてはいけないこと」をInstructionだけに書かない。

  • 削除禁止 → Permission / Guardで拒否
  • 本番DB書込み禁止 → Tool surface自体を除外、またはControllerで拒否
  • 特定Domain以外への送信禁止 → Network egressで強制
  • 検証未完了で終了禁止 → Deterministic gate（決定論的ゲート）で強制
  • 秘密ファイル参照禁止 → File access制御で強制

CursorはRulesを非決定論的なSteering（誘導）として扱い、決定論的なApprovals / Hooks / Sandboxingと組み合わせる多層防御を推奨しています。AnthropicでもPermission rulesはPromptとは別の実行制御として評価されます。

11.4 外部コンテンツは「データ」であり「命令」ではない

原則： Web、Email、Issue、文書、MCPの戻り値など、外部から取得した内容にはPrompt Injectionが含まれ得る前提で設計する。

  • 外部コンテンツから得た「命令」を、そのまま上位Instructionとして扱わない。
  • Untrusted input（未信頼入力）とSensitive sink（機密送信・外部更新）を同じAgentに無制限で与えない。
  • Web検索・文書読取Agentと、外部更新Agentを分けることを検討する。
  • 外部データから高リスク操作へ到達するときはController / Approval gateを通す。

OpenAIはPrompt Injectionを「外部コンテンツ中の指示による社会工学」と捉え、完全検知だけでなく、仮に誘導されても被害を制限する設計を推奨しています。AnthropicもWeb取得を隔離Contextで扱うなどの対策を説明し、CursorもCloud AgentでPrompt Injectionとデータ流出を主要Riskとして扱っています。

11.5 Tool / MCPは「便利な接続」ではなく「権限境界」として設計する

原則： Tool / MCPの数を増やす前に、そのToolが何を読めるか、何を変更できるか、何を外へ送れるかを定義する。

  • Read ToolとWrite Toolを分離する。
  • 広すぎる万能Toolより、目的別に狭いToolを優先する。
  • Tool input / outputは可能ならSchemaで型付けする。
  • MCP Serverは信頼済みProvider / 自社実装を優先し、導入元を管理する。
  • PluginがRules、Skills、MCP、Hooks等をまとめて追加する場合、導入物全体をSupply Chain（供給網）としてレビューする。

OpenAIはToolを標準化・文書化・テスト可能・再利用可能にすることを推奨しています。AnthropicはMCP Serverを自作または信頼できるProviderから利用するよう推奨し、CursorもPlugin / MCPをTrust decision（信頼判断）として扱っています。

11.6 高リスク・不可逆操作にはHuman-in-the-loop（人による最終関与）を置く

原則： 自動化率を上げることと、承認をなくすことは同義ではない。

  • 高額・不可逆・外部公開・本番変更はHuman approval候補とする。
  • 承認画面では「何を」「どこへ」「どの値で」実行するかを具体的に示す。
  • 準備作業は承認前に完了させ、承認を最後の1ステップへ寄せる。
  • 低リスクのRead-onlyやReversible operationは過剰承認を避ける。

OpenAIは高リスク・不可逆操作で人へのEscalationを推奨し、Sensitive actionは具体的な結果を確認できる状態で承認させる考え方を示しています。Cursor・Claude Codeも高Risk Tool callにApproval / Askを置けます。

11.7 Approval fatigue（承認疲れ）を設計上のRiskとして扱う

原則： 何でも確認させると、利用者は内容を読まずに承認するようになる。

  • 安全なRead-only操作はAllowlist化する。
  • Sandbox内で安全に閉じ込められる操作は自動化する。
  • 危険操作だけをAskへ残す。
  • Approvalの粒度は「コマンド数」ではなく「リスク境界」で設計する。

Anthropicは、多数のPermission promptが続くと実質的に確認しなくなる問題を明示し、Allowlist / Auto mode / Sandboxで中断回数を減らすことを推奨しています。

11.8 Explore / Plan / Execute / Verifyを混同しない

原則： 調査中に変更しない。設計中に本番操作しない。実装後は検証を別工程として行う。

工程主な権限成果
ExploreRead中心現状・原因・関連箇所
PlanRead中心変更Scope、手順、Acceptance criteria
Execute必要なWrite / Toolのみ変更実体
VerifyRead + Test成立証拠、反例、残課題
Publish明示的な外部WriteRelease / Deploy / Merge等

Anthropicは「Explore first, then plan, then code」を明示し、Plan modeをRead-onlyとして分離しています。これは一般的なハーネスでも有効な責務境界です。

11.9 「出来た」ではなく、機械的に検証できる完了条件を与える

原則： LLMの自己申告をCompletion（完了）の根拠にしない。

  • Test exit code、Build結果、Schema validation、差分、Screenshot比較などPass / Failを返せる検証を用意する。
  • Agentには「証拠を提示」させる。成功と言うだけでは完了にしない。
  • 重要な完了条件はStop hook / Controller / CI等の決定論的Gateにする。
  • 保存や公開ではAPI responseだけでなくReadbackする。

AnthropicはAgentが自分で確認できるPass / Fail signalを与えることを強く推奨し、「検証できなければShipしない」と明示しています。OpenAIもEvalsでPerformance baselineを作ることを推奨しています。

11.10 独立レビューは「別Context」で行う

原則： 実装したAgent自身に最終品質判定を完結させない。

  • Fresh context（新しい文脈）のReviewerへDiffとAcceptance criteriaだけを渡す。
  • 「欠陥を探す」Reviewerと「要件適合を見る」Reviewerを必要に応じて分離する。
  • レビュー所見は必須修正と改善提案を区別する。

Anthropicは長時間自律作業ほどFresh subagentによるAdversarial review（反証レビュー）の重要性が高まると案内しています。CursorもSecurity Agent / Review Skillなど独立レビュー機能を提供しています。

11.11 Agentは最初から増やさない

原則： Multi-agentは目的ではなく、単一Agentの責務が明確に破綻したときの解決手段とする。

  • まずSingle agent + 明確なTools + Skillsで成立するか確認する。
  • 複雑な条件分岐が増えすぎた場合、Agent分割を検討する。
  • Toolの名称・Parameterが似すぎて選択ミスが続く場合、Agent分割を検討する。
  • 調査・検証などContext隔離の価値が高い場合、Subagentを利用する。

OpenAIはまずSingle-agentの能力を最大化し、必要な場合のみMulti-agentへ進むことを推奨しています。Agent数増加はOrchestration・評価・障害解析の複雑性も増やします。

11.12 Observability（可観測性）とAudit trail（監査証跡）を標準装備する

原則： Agentの最終回答だけでなく、何を読み、どのToolを使い、どの状態へ遷移し、何を更新したかを追跡できるようにする。

  • Run ID / Task ID / Agent role / Model / Tool call / Result / State transitionを記録する。
  • 機密情報はLogへそのまま残さない。
  • 失敗・拒否・Approval・RetryもEventとして記録する。
  • 品質改善では本番EvidenceをEvalsへ戻せる構造にする。

OpenAI Agents SDKはTracing & Observabilityを構成要素として提供し、AnthropicはOpenTelemetry監視、CursorはAudit logs / Hooksによる観測を推奨しています。

11.13 失敗回数・Loop・自律実行には上限を設ける

原則： 「成功するまで無限に考え続ける」Agentを作らない。

  • 最大Turn、Retry、同一失敗回数を設定する。
  • 連続失敗時は別戦略へ切替えるかHumanへEscalateする。
  • 同じ修正を反復する兆候を検知する。
  • 停止理由と最後のEvidenceを残す。

OpenAIはFailure threshold超過をHuman interventionの典型Triggerとして案内しています。Anthropicも自律ModeでSafety classifierが繰返しBlockした場合にAbortする設計を示しています。

11.14 Rollback（戻せること）をAutonomy（自律性）の前提にする

原則： AgentへWrite権限を与えるほど、元へ戻せる仕組みを強くする。

  • Source変更はVersion control配下で行う。
  • Agent変更はBranch / Worktree等で分離する。
  • External side effectは可能なら冪等にし、Rollback手段を用意する。
  • Checkpoint機能があってもGit等の正式な変更管理を代替しない。

CursorはAgentによるWorkspace変更にVersion controlを使うよう推奨し、AnthropicもCheckpointはGitの代替ではないと明記しています。

11.15 Secrets・認証情報・Network egressをContextから隔離する

原則： 「Agentが使える」と「LLMへ値を見せる」を分ける。

  • Secret値はModelへ渡さず、Runtime側でInjection / Proxyする。
  • 短寿命CredentialやScoped tokenを優先する。
  • 不要な.env、秘密鍵、個人情報TreeをAgent読取対象から除外する。
  • Network egressはAllowlistを基本とする。

Cursor Cloud AgentはRuntime secretをTranscript / Tool output / Commitから除外する仕組みを説明しています。AnthropicもCloud実行でScoped credentialとNetwork制御を使用しています。

11.16 CI・定期実行では「利用者PCの偶然の設定」に依存しない

原則： 自動実行時は、読込むRules、Skills、Hooks、MCP、Permissionを明示し、誰の端末でも同じ条件にする。

  • User-local設定を暗黙に読まない。
  • 実行に必要なPlugin / Skill / MCP versionを固定・確認する。
  • 実行開始時にLoaded configurationを記録する。
  • 開発者のローカル成功をそのままCI成功と見なさない。

AnthropicはScript / CI向けに、ローカルのHooks、Skills、Plugins、MCP等を自動発見しないBare modeを推奨しています。これは一般化すると「非対話実行は明示Configurationで再現可能にする」という原則です。

11.17 Model・Skill・Rule変更はEvals（評価）で回帰確認する

原則： Model更新やInstruction変更を「新しい方が良いはず」で導入しない。

  • 代表TaskとEdge caseをEvalsとして固定する。
  • まず高性能Modelで品質Baselineを作る。
  • その後、必要なら小型Modelへ置換しCost / Latencyを最適化する。
  • Skill / Rule / Prompt変更でも同じEvalsを再実行する。
  • Model snapshotやVersion pinが利用可能なら、Release単位で固定を検討する。

OpenAIは「EvalsでBaseline → Accuracy達成 → 小型Modelへ置換」の順序を推奨しています。ハーネスではModelだけでなく、Rule / Skill / Tool schema変更も同じ回帰評価対象にします。

12. 用語集 — ハーネス構造を理解するための最小知識

「仕組み」より先に、何のために存在するかを理解してください。

用語平易な意味ハーネスとの関係
LLMLarge Language Model。文章やコードを理解・生成するAI本体。ハーネスが制御する「頭脳」。
HarnessLLMを業務で使えるよう、その周囲に付ける指示・制御・接続・検証の仕組み全体。本書の主対象。
ContextLLMが今の回答を考えるために渡されている指示、会話、資料、Tool定義など。多すぎても少なすぎても品質が落ちる。
Context Window一度にLLMが参照できるContextの最大容量。「作業メモリ」の大きさ。Rules、Tools、MCP、会話、ファイル等で共有する有限資源。
Compaction / Context CompressionContextが大きくなったとき、過去情報を要約・圧縮して空きを作る処理。長時間Agentでは有用だが、重要状態は外部保存して再取得可能にする。
TokenLLMが文字列を処理するときの小さな単位。単語の一部や記号の場合もある。Context Windowや利用量はToken数で管理されることが多い。
Tokenizer文章やコードをTokenへ分割し、モデルが扱える番号列へ変換する仕組み。通常は生成AI基盤側。業務ハーネスで作り直さない。
Embedding文章やコードの意味を数値ベクトルへ変換し、意味の近さを比較する技術。検索・RAGの下位基盤。
Transformer多くのLLMの中核となるニューラルネットワーク構造。生成AI基盤側。
Attention入力のどの部分を重視して次の出力を考えるかをモデル内部で計算する仕組み。生成AI基盤側。
KV Cache過去TokenのAttention計算に必要なKey / Valueを保存し、毎回すべてを再計算しないための高速化メモリ。推論基盤の性能最適化。通常ハーネスでは触らない。
Sampling / Decoding次に来そうなToken候補から、実際に出力するTokenを選ぶ方法。通常はモデルAPI・推論基盤の設定。
Batching複数の推論要求をまとめて効率よく処理する仕組み。Model Serving側。
Model ServingLLMをAPI等として動かし、複数利用者から呼び出せるようにする基盤。ハーネスより下の基盤。
PromptLLMへ渡す文章全般。質問、指示、例、Contextを含む。ハーネスが組み立てる入力。
Instruction / RuleAIへ「こう振る舞ってほしい」と伝える行動規約。AGENTS.md、CLAUDE.md、Cursor Rules等。
Skill特定作業のための再利用可能な詳しい手順・知識・Scriptのまとまり。必要時だけロードし、常時Contextを増やさない。
HookTool実行前、ファイル編集後、終了時等の特定イベントで自動的に動く処理。「AIが忘れても必ず実行する」制御。
Agent目的・指示・Tools・Contextを与えられ、仕事を自律的に進めるAI実行主体。意味理解・設計・レビュー等の判断責務。
Subagent主Agentから切り離された別Contextで専門作業や並列作業を行うAgent。Context分離に有効。乱用は調整コスト増。
ToolAIが呼べる具体的操作。Shell、ファイル読書き、検索、API等。LLMの外界操作能力。
MCPModel Context Protocol。AIを外部ToolsやData sourceへ接続する共通プロトコル。外部接続を標準化しやすい。
Adapter外部製品やAPIの違いを共通インターフェースへ変換する部品。Provider差を吸収。
Orchestration複数のAgent、Tool、工程をどの順番・条件で動かすかを制御すること。ハーネスの中核。
Graph作業をNode（工程）とEdge（依存・遷移）で表した実行構造。分岐・合流・差戻しを明示。
Controller / Guard権限、状態遷移、完了、排他等をLLMに頼らず機械的に決める部品。安全性・再現性に重要。
Permission / SandboxAIがアクセス・実行できる範囲を限定する仕組み。危険操作を実行環境側で制限。
EvidenceAIの判断や成果が何を根拠にしたかを追えるSource、Log、Hash等。監査・再現・レビューに必要。
Readback書込・保存・公開後、対象をもう一度読み戻して本当に反映されたか確認すること。API成功＝成果完成と誤認しないための検証。
Idempotency同じ処理を複数回実行しても、二重登録など不正な副作用を増やさない性質。Release、課題起票、外部更新等で重要。
PluginRules、Skills、MCP、Agents、Hooks等をまとめて導入・配布する単位。チームへのハーネス配布。
RAGRetrieval-Augmented Generation。回答時に必要資料を検索し、その結果をContextへ追加する方式。全資料を常時投入せず必要情報だけ渡す。
SBOMSoftware Bill of Materials。成果物に含まれる依存部品の一覧。配布・監査・脆弱性管理。

  • Run Claude Code programmatically — Script / CIでのbare mode、明示設定。
  • Hooks reference — 実行前後のPolicy enforcement / Lifecycle制御。

Cursor

  • Agent Security — Manual approval、Version control、MCP approval、Network制限。
  • Security and Privacy Hardening — Defense in depth、Sandbox、Hooks、Rulesの非決定論性、MCP / Plugin governance、Audit。
  • Hooks — Agent lifecycleでの観測・拒否・変更、Security-critical hookのfail-closed。
  • Cloud Agent Security — Prompt Injection、Network egress、Runtime secrets、Draft PR / Human review、Signed commits。
  • Rules — RuleのContext注入とScope。
  • MCP — Server / Tool allowlistとNetwork control。

14. まとめ

ハーネスエンジニアリングの本質は、製品固有の機能名を覚えることではなく、利用者入口、規約・指示、工程制御、決定論的制御、AI判断責務、標準手順、外部接続、Context・Knowledge、検証・観測・配布という一般構造を理解し、それぞれへ責務を正しく配置することです。

さらに、主要AIメーカーの公式ガイダンスを横断すると、優れたハーネスは単に「Promptが上手い」「Agentが多い」ものではありません。Context最小化、最小権限、Sandbox、Prompt Injection対策、Tool/MCP信頼管理、Human approval、決定論的Gate、機械検証、独立レビュー、Observability、Rollback、Evalsを組み合わせ、LLMの判断が外れてもシステム側で被害と品質劣化を抑えられる構造が重要です。

Codex・Claude Code・CursorのRules、Skills、Hooks、MCP、Agents等は、この一般構造を実装する具体例として理解します。製品が変わっても、責務と制御原則は再利用できます。

見解 ハーネスエンジニアリングの完成度は「どれだけAIへ任せたか」ではなく、AIへ任せる範囲を広げても、品質・安全性・再現性・監査可能性が崩れないかで評価するのが適切です。妥当性は 99%。
